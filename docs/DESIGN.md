## D1. 청크 크기를 토큰으로, 그것도 임베딩 모델의 토크나이저로 잰다

**문제**
책은 학술 논문 기준으로 512~1,024 토큰 청크에 20% 중첩을 권장합니다. 그런데 책이 쓰는 all-MiniLM-L6-v2를 실제로 로드해 보면 `max_seq_length`가 **256**입니다. 이 한도를 넘는 입력은 오류 없이 뒷부분이 잘린 채 임베딩됩니다. 즉 512토큰 청크는 앞쪽 절반만 벡터에 반영되고, 뒤쪽 절반은 검색으로 절대 찾을 수 없는 텍스트가 됩니다.

**결정**
- 청크 크기를 문자 수나 단어 수가 아니라 **임베딩 모델 자신의 토크나이저**로 셉니다 (`Embedder.count_tokens`)
- 목표 200토큰, 중첩 20%. 특수 토큰 2개(`[CLS]`, `[SEP]`)를 더해도 256 안에 들어오도록 했고, 설정값이 한도를 넘으면 적재를 시작하기 전에 실패시킵니다 (`pipeline.ingest`)
- 문장 경계를 지키며 채우고, 200토큰을 넘는 한 문장(표, 수식)만 단어 경계로 자릅니다
- 청크는 섹션 경계를 넘지 않고, 첫 문장의 쪽 번호를 가집니다

**대안**
더 긴 입력을 받는 모델(예: 512토큰 모델)로 바꾸고 책의 크기를 따르는 방법. 이 경우 384차원 스키마와 모델 다운로드 크기가 함께 바뀝니다. 이 저장소는 책과 같은 모델을 쓰면서 그 한도에 맞추는 쪽을 택했습니다.

**대가**
청크 수가 늘어납니다(논문 1편당 약 40~100개). 행 수와 HNSW 그래프 크기가 커지지만, 이 규모(수천~수만 청크)에서는 문제가 되지 않습니다.

**검증**: `stats` 명령의 `tokens / chunk max`가 200 이하인지 확인 ([02_stats.svg](images/02_stats.svg))

**실제로 잡은 버그**
첫 적재 후 `stats`에서 최대 357토큰 청크가 나왔습니다. PDF에 섞여 있던 LaTeX 그림 메타데이터(`sha1_base64="..."`)가 공백 없는 한 단어라서, 단어 경계로 자르는 로직이 쪼개지 못한 것입니다. 두 겹으로 막았습니다.
- 추출 단계: 공백 없이 80자 넘는 토큰(base64, 긴 URL)을 제거
- 청커: 그래도 목표를 넘는 단어는 문자 단위로 잘라 **어떤 입력에도** 한도를 보장 (`test_limit_holds_for_huge_unbroken_token`)
수정 후 재적재에서 최대 200토큰.

## D2. 저자는 정규화한 이름으로 중복 제거하고, 순서를 보존한다

**문제**
책의 `_upsert_paper`는 `INSERT INTO authors ... ON CONFLICT (name)`을 쓰지만, 같은 책의 스키마에서 UNIQUE 제약은 `normalized_name`에만 있습니다. PostgreSQL은 ON CONFLICT 대상과 일치하는 제약이 없으면 `there is no unique or exclusion constraint matching the ON CONFLICT specification` 오류를 냅니다. 또 `return`이 저자 루프 안에 있어 첫 저자만 처리되고, `author_position`을 넣지 않아 저자 순서가 사라집니다.

**결정**
- `normalized_name`(소문자, 악센트 제거, 마침표 제거, 공백 정리)을 UNIQUE 키로 쓰고 `ON CONFLICT (normalized_name)`
- `DO NOTHING` 대신 `DO UPDATE SET name = authors.name`: 충돌해도 `RETURNING id`가 행을 돌려주므로 "INSERT 실패 시 SELECT로 다시 조회"하는 두 번째 왕복과 그 사이의 경합이 사라집니다
- `paper_authors.position`에 1부터 시작하는 순서를 저장
- 논문을 다시 적재하면 그 논문의 저자 관계를 지우고 다시 만듭니다 (개정판에서 저자가 바뀌는 경우)

**대안**
ORCID 같은 외부 식별자로 저자를 구분하는 방법. arXiv API는 ORCID를 주지 않아 이름 정규화가 현실적인 선택입니다. 동명이인은 같은 사람으로 합쳐지는 한계가 남습니다.

## D3. 메타데이터 필터와 벡터 검색을 한 SQL에 두고, HNSW 반복 스캔을 켠다

**문제**
4장(sqlite-vss)에서는 FAISS가 메타데이터를 모르기 때문에 "후보를 10배 가져와서 SQL로 거르는" 초과 조회 패턴을 썼습니다. pgvector는 벡터와 메타데이터가 같은 테이블·같은 쿼리 플래너 안에 있으니 이 문제가 사라질 것 같지만, 그렇지 않습니다. HNSW 인덱스 스캔은 `ef_search`개 후보를 만든 뒤 필터를 적용하므로, 필터 조건이 드물면 `LIMIT 10`을 요청해도 그보다 적게 돌아옵니다.

**결정**
- 필터(카테고리, 저자, 날짜)는 별도 단계가 아니라 벡터 검색 SQL의 `WHERE`에 넣습니다. 모든 값은 바인딩 파라미터로만 전달합니다 (`build_filter`)
- 트랜잭션마다 `SET LOCAL hnsw.iterative_scan = relaxed_order`를 켭니다. pgvector 0.8부터 지원하는 기능으로, 필터 후 결과가 모자라면 인덱스를 이어서 더 탐색합니다
- `relaxed_order`는 결과 순서가 약간 어긋날 수 있어 애플리케이션에서 거리로 한 번 더 정렬합니다
- `SET LOCAL`을 쓴 이유: 커넥션 단위 `SET`은 풀링 환경에서 다른 요청으로 새어 나갑니다

**측정** ([07_bench.svg](images/07_bench.svg))
"retrieval augmented generation" 쿼리에 드문 카테고리(cs.CV) 필터를 걸고 HNSW 경로를 강제했을 때, 반복 스캔을 끄면 요청한 10건보다 적게, 켜면 10건이 모두 돌아옵니다. 실행 계획은 [06_explain_filter_hnsw.svg](images/06_explain_filter_hnsw.svg): HNSW 인덱스가 142행을 읽어 조건에 맞는 10건을 채웠습니다. 기본 후보 수(`ef_search` = 100)보다 더 읽은 것이 반복 스캔이 동작한 흔적입니다.

**대안**
- 카테고리별 부분 인덱스(`WHERE 'cs.CV' = ANY(categories)`): 필터 값이 고정적이고 적을 때 가장 빠르지만 카테고리마다 인덱스가 생깁니다
- `strict_order`: 순서는 정확하지만 더 느립니다

## D4. 하이브리드 검색은 점수 합산이 아니라 RRF로 섞는다

**문제**
책의 검색 엔진 골격은 벡터 결과와 키워드 결과를 가중치로 합치는 `_combine_results(vector_weight, keyword_weight)`를 예고합니다. 하지만 코사인 거리(0~2)와 `ts_rank_cd`(문서·쿼리에 따라 범위가 달라짐)는 스케일이 달라서, 원점수를 더하면 한쪽이 결과를 지배하고 가중치의 의미가 쿼리마다 바뀝니다.

**결정**
Reciprocal Rank Fusion: 청크마다 `Σ 1 / (60 + 순위)`. 점수가 아니라 **순위**만 쓰므로 스케일 정규화가 필요 없습니다. 두 목록에 모두 나온 청크가 자연스럽게 위로 올라옵니다.

**보는 법** ([05_mode_keyword.svg](images/05_mode_keyword.svg), [05_mode_vector.svg](images/05_mode_vector.svg))
"BM25" 같은 고유 용어는 키워드 검색이 정확히 잡고, 표현이 다른 같은 의미는 벡터 검색이 잡습니다. 하이브리드는 둘 다 놓치지 않는 쪽을 노립니다.

**대가**
"얼마나 비슷한가"라는 절대값은 사라집니다. 그래서 화면에는 RRF 점수 대신 가장 가까운 청크의 코사인 유사도를 함께 보여 줍니다.

## D5. 검색 단위는 청크, 결과 단위는 논문

**결정**
- 벡터·키워드 후보는 청크 단위로 `limit × 5`개 가져옵니다 (한 논문이 여러 청크로 걸리므로)
- 논문 점수 = 그 논문에서 가장 좋은 청크의 점수. 화면에는 가장 잘 맞은 구절과 섹션·쪽 번호를 함께 보여 줍니다
- 초록은 PDF가 아니라 arXiv 메타데이터에서 가져와 청크로 만듭니다. PDF 첫 쪽의 초록은 다단 배치·각주와 섞여 품질이 떨어집니다

**대안**
논문 점수를 매칭 청크 수나 상위 3개 평균으로 매기는 방식. 긴 논문이 짧은 논문보다 유리해지는 편향이 생겨 최고 청크 방식을 택했습니다.

## D6. PDF는 블록 좌표로 읽기 순서를 복원한다

**문제**
학술 논문은 2단 편집이 많아서, 페이지 텍스트를 그대로 뽑으면 왼쪽 단과 오른쪽 단의 줄이 섞입니다. 머리글·바닥글·쪽 번호·왼쪽 여백의 arXiv 스탬프도 본문에 끼어듭니다.

**결정** (`pdf.py`)
- PyMuPDF의 텍스트 **블록**(좌표 포함)을 받아, 양쪽 단에 블록이 2개 이상이면 2단으로 판단하고 "위쪽 전체 폭 → 왼쪽 단 → 오른쪽 단 → 아래쪽 전체 폭" 순서로 정렬합니다
- 페이지의 3분의 1 이상에 반복되는 짧은 줄은 머리글·바닥글로 보고 버립니다
- 섹션 제목을 인식해 청크에 섹션 이름을 붙이고, References에서 멈춥니다. 제목과 첫 문장이 한 블록에 붙은 경우("1 INTRODUCTION To invent ...")는 분리합니다
- PDF 처리에 실패하면 논문을 버리지 않고 초록만으로 색인합니다 (`papers.error`에 사유 기록)

**한계**
수식은 텍스트로 깨지고, 표는 셀 순서가 섞입니다. 표·수식이 중요한 논문이라면 GROBID 같은 학술 PDF 전용 파서가 다음 단계입니다.

## D7. 쓰기 경로: 논문 1편 = 트랜잭션 1개, 임베딩은 트랜잭션 밖

**결정**
- 임베딩 계산(수 초)을 먼저 끝내고 나서 트랜잭션을 엽니다. 느린 모델 호출이 행 잠금을 잡고 있지 않습니다
- 논문 메타데이터 UPSERT, 저자 관계, 청크 교체(DELETE 후 INSERT), 상태 갱신을 한 트랜잭션으로 묶습니다. 중간에 실패하면 그 논문만 롤백되고, "청크는 새것인데 상태는 옛것"인 상태가 생기지 않습니다
- arXiv ID는 버전 접미사(v1, v2)를 떼고 저장합니다. 개정판을 다시 적재하면 같은 행이 갱신됩니다
- 이미 같은 `updated` 날짜로 임베딩된 논문은 건너뜁니다 (`--refresh`로 강제 재처리)

**4장과 비교**
sqlite-vss는 벡터가 별도 가상 테이블에 rowid로만 연결돼 있어 `INSERT OR REPLACE` 한 번으로 매핑이 깨졌습니다. 여기서는 청크와 벡터가 같은 행이고 외래 키 `ON DELETE CASCADE`가 걸려 있어, 논문을 지우면 청크와 벡터가 함께 지워집니다.

## D8. 임베딩은 L2 정규화해서 저장하고, 연산자와 인덱스 연산자 클래스를 맞춘다

- `normalize_embeddings=True`로 길이 1 벡터를 저장합니다. 이러면 코사인 거리, 내적, 유클리드 거리의 순위가 같아져 나중에 연산자를 바꿔도 결과 순서가 유지됩니다
- 인덱스는 `vector_cosine_ops`, 쿼리는 `<=>`. 연산자와 연산자 클래스가 다르면(예: 인덱스는 코사인인데 쿼리는 `<->`) 플래너가 인덱스를 쓰지 못하고 전체 스캔으로 떨어집니다

## D9. 규모가 작으면 플래너는 HNSW를 쓰지 않는다 (그리고 그게 맞다)

**관찰** ([06_explain_nofilter.svg](images/06_explain_nofilter.svg))
청크 2,147개에서는 필터가 없어도 플래너가 `Seq Scan` + `top-N heapsort`를 고릅니다. 384차원 벡터 2천여 개를 전부 비교해도 수 ms라, 인덱스를 타는 비용보다 싸다고 판단한 것입니다. 책이 "10만 개 미만이면 Flat(정확 검색)으로 충분"이라고 한 기준이 실행 계획으로 확인됩니다.

**결정**
- 필터가 없을 때는 `papers` 조인을 뺀 단일 테이블 쿼리를 씁니다. `ORDER BY distance LIMIT k`만 남아야 데이터가 커졌을 때 플래너가 HNSW 인덱스 순서로 k개만 읽고 멈출 수 있습니다
- `bench`와 `explain --force-index`는 `enable_seqscan = off`로 HNSW 경로를 강제해, 작은 코퍼스에서도 인덱스 동작(재현율, 반복 스캔)을 관찰할 수 있게 했습니다

## D10. 실행 환경 고정

- Intel Mac에서 쓸 수 있는 마지막 PyTorch가 2.2.2라서, 최신 transformers(5.x)와 sentence-transformers(6.x)는 import 단계에서 실패합니다 (`NameError: name 'nn' is not defined`). `transformers==4.44.2`, `sentence-transformers==3.1.1`로 고정했습니다
- PostgreSQL은 `pgvector/pgvector:pg16` 이미지로 띄우고, 스키마는 `docker-entrypoint-initdb.d`로 첫 기동 때 자동 적용합니다

## 책과 달라진 점 요약

| 항목 | 책 (5장) | 이 저장소 |
|---|---|---|
| 청크 크기 | 512~1,024 토큰, 20% 중첩 | 200 토큰(모델 토크나이저 기준), 20% 중첩, 한도 초과 시 적재 거부 |
| 저자 UPSERT | `ON CONFLICT (name)` (제약 불일치로 오류), 첫 저자만 처리 | `ON CONFLICT (normalized_name)` + `RETURNING`, 저자 순서 보존 |
| 필터 결합 | 하이브리드 검색 골격 | 같은 SQL의 `WHERE` + `hnsw.iterative_scan` |
| 하이브리드 점수 | 가중치 합산 골격 | RRF |
| 구현 범위 | 클래스·메서드 골격 (본문은 깃허브 참조) | 수집부터 검색, 측정까지 동작하는 구현 + 단위 테스트 |
